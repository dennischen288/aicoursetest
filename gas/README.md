# 炙餃 Google Sheets／GAS 訂單後端

第一版接受外帶、內用，由店家確認後付款。不處理線上金流；收到訂單不代表店家已確認。

## 初始化（不需先建立試算表）

1. 在 https://script.google.com 建立新專案，名稱可填「炙餃訂單後端」。
2. 將 `Code.gs` 全文貼入編輯器，取代預設內容。
3. 在專案設定開啟「在編輯器中顯示 appsscript.json」，貼入本資料夾的 `appsscript.json`。時區為台北。
4. 選擇 `setup` 並執行，使用你的 Google 帳號授權試算表存取。此步驟需要由試算表擁有者操作。
5. 執行記錄會輸出新建試算表網址；專案設定的指令碼屬性也會保存 `SPREADSHEET_ID`。再次執行 `setup()` 會沿用同一份試算表，不會覆蓋既有商品或訂單。
6. 確認「商品」的名稱、單價和上架狀態。程式內的初始價格沿用目前示範網站，正式接單前務必確認。商品調價時也要同步網站價格，金額不符的訂單會被拒絕。
7. 第一版門市代碼是 `main`；訂單都送到同一門市，請先確認網站門市資料。
8. 確認完成後，在 GAS 執行 `enableOrders()`。要暫停接單則執行 `disableOrders()`。

## 部署 GAS

1. 點「部署 → 新增部署作業」，選擇「網頁應用程式」。
2. 執行身分選擇「我」，存取權限選擇「任何人」。此設定只公開訂單接收端；**試算表維持私人**，不需公開分享。
3. 部署後複製 `https://script.google.com/macros/s/…/exec` 網址。請使用 `/exec`，不要使用只限開發者的 `/dev`。
4. 開啟該網址會回傳服務狀態 JSON。啟用後應有 `"acceptingOrders":true`；它不會回傳訂單或顧客資料。
5. 將 `/exec` 網址交回前端串接。網站端的公開設定為 `checkout-config.js`：確認測試成功後才將 `enabled` 設為 `true`。
6. **後續更新 GAS 原始碼**：需再到「管理部署作業 → 編輯 → 新版本 → 部署」，才能更新 `/exec` 使用的程式。只按儲存不會更新正式端點。

若 Workspace 管理員不允許「任何人」，此匿名接單方案無法使用，需要管理員開放或改用其他後端。

## 工作表

- **訂單**：一筆訂單一列，包含編號、台北時間、接單及付款狀態、門市、取餐方式、姓名、電話、備註、商品摘要、總數量、總金額、商品 JSON、請求 ID 與內容雜湊。
- **商品**：商品代碼、名稱、整數單價、上架勾選。單價由後端讀取；前端不能自行指定有效價格。
- **使用說明**：記錄店家操作方式。

狀態由店家在「訂單」C、D 欄更新。第一版沒有把後台狀態回推給顧客，也沒有寄送通知。

## 前端傳輸協定

跨網域使用 **HTML 表單 POST → 隱藏 iframe → postMessage 回覆**。GAS HtmlService 會加入自己的沙箱 iframe，因此使用 Google HTTPS 回覆來源、隨機 nonce、請求 ID 驗證，不依賴 fetch 的 CORS 回應，也不把姓名、電話放入 URL。

POST 採 `application/x-www-form-urlencoded`，欄位：

- `payload`：以下 JSON 的字串。
- `nonce`：前端每次傳輸產生的 32 位十六進位亂數。
- `website`：蜜罐欄位，正常使用者應留空。

```json
{
  "version": 1,
  "requestId": "8bf7a728d8d549ad93cb190f6ccdf671",
  "storeId": "main",
  "fulfillment": "外帶",
  "customer": {"name": "測試顧客", "phone": "0900000000", "note": "測試訂單，請勿製作"},
  "items": [{"id": "p01", "quantity": 2}],
  "expectedTotal": 170
}
```

GAS 完成試算表寫入與 `SpreadsheetApp.flush()` 後，才向網站來源送出：

```json
{
  "channel": "zhijiao-order-v1",
  "nonce": "前端傳來的亂數",
  "requestId": "前端傳來的請求ID",
  "ok": true,
  "orderId": "ZJ-20261116-A1B2C3D4E5F60718",
  "total": 170
}
```

失敗時 `ok:false`，包含 `code` 與可顯示的 `message`。網站必須保留購物車，不能把逾時或 iframe 載入當成送單成功。結果不明時，以**相同 requestId 和相同內容重試**；後端會回傳既有訂單，不重複寫入。

## 指令碼屬性

| 名稱 | 來源／用途 |
| --- | --- |
| `SPREADSHEET_ID` | `setup()` 自動產生；既有試算表也可事先填入 ID。 |
| `SITE_ORIGIN` | 預設 `https://dennischen288.github.io`。這是回覆目的來源，不含 `/aicoursetest/` 路徑，也不是存取驗證密鑰。更換網域時需更新。 |
| `ORDERS_ENABLED` | 預設 `false`；由 `enableOrders()`／`disableOrders()` 切換。 |

## 驗收

使用明確標記「測試訂單，請勿製作」的虛構資料：

1. 送出 2 份 `p01`，檢查新增一列、金額 170、狀態「待確認／未付款」。
2. 相同請求 ID 重送，確認仍只有一列且回覆同一個訂單編號。
3. 將 `expectedTotal` 改為 1，必須回覆 `PRICE_CHANGED` 且不新增資料。
4. 測試宅配、負數、零數量、不存在及已下架的商品，全部拒絕。
5. 暫停接單後送新訂單，必須回覆 `CLOSED`。
6. 斷網或無法收到回覆時，網站不能清空購物車或顯示成功。

## 容量與資料管理

這是低流量店家的第一版：使用 ScriptLock 序列寫入，單筆最多 20 種商品、每品項 99 份、總數 300 份、總額 NT$50,000；全站每分鐘最多 30 筆新訂單。這些上限可依需求調整。

端點為匿名接單，蜜罐和速率限制只能降低一般誤用，不是完整防機器人或身分驗證。流量增加時應加入伺服器驗證的 CAPTCHA，並評估資料庫與 API 服務。GAS 和 Google Sheets 都受 Google 配額及服務可用性限制。

顧客個資只寫入私人試算表；不要把試算表設成知道連結即可檢視，不要將原始訂單寫入日誌，也不要把 Google 憑證放在網站程式。由店家依實際營運需求設定資料保留與刪除政策。

## 本次完成範圍

提供後端程式、初始化流程及傳輸協定。僅生成檔案**不會**自動建立你帳號內的試算表或部署 GAS；必須完成上述授權與部署。正式接通還需要 `/exec` 網址及端到端測試。

## 本地驗證

執行 `node gas/tests/backend.test.cjs`。使用模擬的 Google 服務測試初始化、商品上架、重新計價、重複送單、公式注入防護、拒絕宅配及錯誤數量；不會連線 Google 或產生真實訂單。仍需部署後測試 GAS HtmlService 回覆與試算表實際寫入。
